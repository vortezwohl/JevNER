# JevNER 性能实验报告（v3）

日期：2026-11-03
环境：Windows 11 / Python 3.11.15 / uv 管理依赖 / System One 代理网关
默认模型：baseten/mammoth-1（本版新增与 jev-latest 的同口径对比，见 §7）
实验脚本：`tests/bench_quick.py`（精简单进程版；单样本测量，控制计费成本）
本报告 v3 在 v2 基础上新增模型切换（jev-latest → baseten/mammoth-1）与
两模型对比章节；§2–§6 的 jev-latest 数据沿用 v2 实测值（同脚本同口径）。

## 1. 当前架构口径（与旧版的差异，直接影响性能读数）

| 维度 | 旧版口径 | 本版口径 | 性能影响 |
| --- | --- | --- | --- |
| 窗口大小 | 240k token | 12k token（65,535 字节请求体硬限制换算） | 短文本无感，超长文本窗口数增多 |
| 分型 criteria | label + 全部类型描述 | 仅 label（描述只在 state 类型表出现一次） | 单问题体积 ~2KB → ~150B |
| 实体输出 | 同类型交叠吸收 | 嵌套实体全部保留（福建/福州/福建福州 共存） | 分型问题数随嵌套子 span 数暴涨（约 ×5~9） |
| 检测批次 | 256 问/批 | 64 问/批（抗批内干扰） | 检测请求数 ×4 |
| 检测稳定性 | 单轮 + 灰色区复检一轮 | 灰色区三轮复检取最大（阈值 0.25） | 附加 0~3 轮检测请求 |
| 类型体系 | 封闭枚举 | 开放 taxonomy（JSON 可自定义） | 类型表进 state，类型越多 state 越大 |
| 默认模型 | jev-latest | baseten/mammoth-1（网关同协议路由） | mammoth-1 校验更严：单请求选项总数 ≤512（分型批按选项预算动态收窄至约 25 问/批） |

## 2. 实验结果

### E1 单文本端到端延迟（串行，max_workers=1，with_gender=True）

| 文本 | token 数 | 延迟 | 实体数（含嵌套子层） |
| --- | --- | --- | --- |
| 短（16 字） | 16 | 17.5 s | 5 |
| 中（10 句） | 200 | 163.9 s | 98 |
| 长（30 句） | 860 | 139.9 s | 311 |

观察：
- 延迟主要随**分型 span 数**增长而非 token 数——嵌套全保留后，中等文本即可产生近百度分型问题（旧口径下同文本仅 11 个实体）；
- medium 反而慢于 long 属单样本网络噪声（本网关单请求 RTT 波动大），量级可信、次序不可；
- 检测阶段（64 问/批 + 最多三轮复检）贡献了可观的固定请求数。

### E2 缓存收益（同实例二次调用）

| 调用 | 延迟 |
| --- | --- |
| 热调用（检测/分型/性别三级 LRU 全命中） | 5–10 ms |
| 热调用二次确认 | 5 ms |

测量瑕疵如实声明：本轮"冷调用"读数 0.01s 实为 E1 已缓存同文本（实验脚本瑕疵），但两次热调用稳定在 5–10ms 本身即缓存收益的直接证明——**重复/重叠文本近零成本**（重叠窗口、RAG 重查、同文档重跑全部受益）。

### E3 窗口级并行（30 句长文本，window=1024 强制 4 窗口）

| 并行度 | 延迟 | 加速比 |
| --- | --- | --- |
| 1 | 121.8 s | 1.00× |
| 4 | 65.8 s | **1.85×** |

观察：未达理想 4×，瓶颈在 API 网关的限流与单请求 RTT（每窗内部还有分型批并发，多窗叠加后并发请求数接近网关舒适区上限）；实体数 306 vs 310 属 API 采样方差。

### E4 JSON 自定义 taxonomy（C 端路径）

| 项 | 读数 |
| --- | --- |
| `EntityTaxonomy.from_json` 构建 | < 0.1 ms（纯本地，零 API） |
| 自定义体系识别（CORE+ECOM，BRAND 文本） | 5.96 s |
| BRAND 类型命中 | Apple / Nike / Amazon Web Services 全中 |

自定义类型与内置类型在识别路径上完全平权，构建开销可忽略。

## 3. 与旧版数据的量级对比（为什么变慢了）

| 场景 | 旧版（平铺+240k 窗口+256 批） | 本版（嵌套+12k+64 批） | 倍率 |
| --- | --- | --- | --- |
| 短文本 | 8.8 s | 17.5 s | ~2× |
| 中文本 | 11.7 s | 163.9 s | ~14× |
| 长文本 | 36.9 s | 139.9 s | ~4× |

慢的三个来源按贡献排序：
1. **嵌套全保留**：分型 span 数 ×5~9（medium 11 实体 → 98 实体），这是用户明确要求的正确性行为（标准返回即含嵌套），属设计取舍而非退化；
2. **检测批 64 + 三轮复检**：检测请求数约 ×4~6，换取检测召回稳定（此前中文双字地名的间歇性漏检由此修复）；
3. **RetryPolicy 放宽**（max_retries=3、无总预算）：瞬态 5xx 时单请求最多重试三次，个别请求延迟被拉长。

## 4. 调优建议

1. **追求延迟时收窄类型面**：`entity_packs=["BIOMED"]` 代替默认 CORE（19 类型），分型 state 更小、类型竞争更少，判定更准更快；
2. **重复文本天然近零成本**：三级 LRU 缓存按窗口哈希键控，管线级复用无需任何配置；
3. **批量场景用 4 并发**：1.85× 加速是当前网关限流下的实测甜点，更多并发收益递减且增加 5xx 概率；
4. **后续优化方向**（未实施，按预期收益排序）：分型 span 预筛（嵌套子 span 中明显碎片在提交前本地过滤）、检测与分型问题数动态预算（按剩余字节额度自适应批大小）、失败批次的定向重试补齐。

## 5. 方法与局限

- 单样本测量（控制计费，用户明确要求），延迟数据含网络抖动与网关排队噪声：量级可信、个位数与次序不可；
- 所有读数基于本机网络与当前网关限流，跨环境不可直接对比；
- E2"冷调用"读数被缓存污染（见 §2 如实声明），热调用读数有效；
- 未测：8 并发（前版实测 3.17× 后回落，本版为控成本未重复）、超长文本（>12k token）多窗口场景的绝对吞吐。

## 6. 默认模型切换：baseten/mammoth-1 vs jev-latest（同口径对比）

切换动因：网关内多模型同协议路由，一行 `model_name` 即可切换。两模型
同脚本（bench_quick.py）同口径实测：

| 指标 | jev-latest | baseten/mammoth-1 | 变化 |
| --- | --- | --- | --- |
| E1 短文本延迟 | 17.5 s | **11.5 s** | **-34%（更快）** |
| E1 中文本延迟 | 163.9 s | 146.4 s | -11%（略快） |
| E1 长文本延迟（串行） | 139.9 s | 784.1 s | **+460%（大幅变慢）** |
| E3 多窗口串行（workers=1） | 121.8 s | 864.8 s | **+610%（大幅变慢）** |
| E3 多窗口 4 并发 | 65.8 s | 157.4 s | +139%（变慢） |
| E3 并行加速比 | 1.85× | **5.49×** | 并行收益显著更高 |
| E2 缓存热调用 | 5–10 ms | 6 ms | 持平 |
| E4 taxonomy 构建 | <0.1 ms | <0.1 ms | 持平 |
| E4 BRAND 识别 | 5.96s / Apple·Nike·AWS 全中 | 9.10s / Apple·Nike 中（AWS 未中） | 略慢且回召率降 |

结论：**性能没有整体改善，而是"短快长慢"的再分配**——mammoth-1 单请求
RTT 更高，请求数少的短文本受益（-34%），请求数多的长文本/多窗口场景
显著劣化（+460%）；其高 RTT 使窗口级并行的相对收益更大（5.49×）。
附带兼容性差异：mammoth-1 后端校验"单请求选项总数 ≤512"（jev 不校验），
分型批已改为按选项预算动态收窄（512 ÷ 每问选项数 ≈ 25 问/批）。

建议：短文本为主的交互场景用 mammoth-1；长文本批量场景
`JevNER(model_name="jev-latest")` 显式回切。默认值取 mammoth-1 遵循
当前产品决策。

## 7. 结论

当前架构把预算花在正确性上：嵌套关系内含于返回值、检测召回稳定、请求体永不超 65,535 字节——代价是单文本延迟较旧口径上升约 2~14 倍，其中最大头（嵌套全保留的分型问题数）是需求本身决定的。缓存（毫秒级热调用）与并行（1.85×）仍是现成的加速手段，JSON 自定义体系零构建开销、识别路径与内置完全平权。
