# JevNER 性能对比：0.1.0（3001377b）→ 当前（bc58d44）

> 对比基点：`3001377b`（2026-11-04，0.1.0 PyPI 发布版，优化前算法）vs `bc58d44`（2026-11-05，全七阶段优化后）
> 模型：`baseten/mammoth-1`（两次相同）；并发参数相同（max_workers=8）
> 方法：准确率用冻结基准（MSRA/Resume/CLUENER 各 200 句固定种子 + 24 语言用例，严格 F1 = (start, end, type) 三元组精确匹配）同条件对跑；耗时用 git worktree 检出旧版实测头对头
> 报告原始数据：`bench/results/baseline.json`（旧算法）与 `bench/results/final.json`（当前）

---

## 0. 结论速览

| 维度 | 变化 | 说明 |
| --- | --- | --- |
| 识别准确率（严格 F1） | **+11.5 ~ +17.9 个百分点** | 三数据集全升，精度（P）近乎翻倍 |
| 长文档单次调用耗时 | **842.7s → 506.7s（-40%）** | 15k 字实测；旧版约 14 分钟，新版约 8.4 分钟 |
| 批量吞吐（600 句全量基准） | **712.5s → 596.0s（-16%）** | 问题数 -17%、请求数 -22% 的同时 |
| 短文本单次调用延迟 | **99.0s → 166.0s（+68%）** | 默认精度档（compete）以延迟换精度；`typing_strategy="flat"` 恢复并优于旧版 |
| 顺带修复的 0.1.0 缺陷 | 4 处 | 含两处 0.1.0 上长文档/自定义类型输出**本来就是错的**的缺陷 |

一句话：**准确率大幅上升、长文档与批量吞吐明显变快；单句调用的默认档延迟上升，是刻意用延迟换精度与成本的取舍（可一键切回低延迟档）**。

## 1. 我们做了哪些优化（七个阶段）

| 阶段 | 内容 | 一句话机制 |
| --- | --- | --- |
| ① 协程并发化 | 线程池 → 单守护线程事件循环 + 信号量 | 检测批从**窗口内串行**改为全部并发（旧版满窗口约 188 次串行往返）；灰区重查 3 轮并发；顺带消除线程池理论死锁 |
| ② 用量计量 + 冻结基准 | `ner.usage` 属性 + `bench/` | requests/questions/cache_hits/tokens/秒全可见；固定种子抽样三数据集各 200 句入库，成为后续一切 A/B 的裁决场 |
| ③ Schema 工程 | 类型正反例 + 否决选项 | `EntityType` 增 examples/counter_examples/min_chars/书名号字段并渲染进类型表；打型增加 PARTIAL（残缺）/MIXED（粘词）显式否决类；NONE 选项写足否决描述 |
| ④ 状态与缓存重构 | 邻域化 + 窗口无关键 | 检测请求 state 从整窗（≤48KB）改为批邻域（±128 token）；打型 state 改位置聚类局部切片；缓存键与窗口解耦并携带完整类型指纹；检测批按绝对位置对齐 + 单飞（single-flight）去重重叠窗口的并发重复问题 |
| ⑤ 候选剪枝 + 竞争打型 | 零成本剪枝 + span 互为选项 | 虚词边缘与检测分边界先验两个本地过滤器；候选 span 作为同一道选择题的选项互相竞争（碎片在完整名面前失去概率），短名单再精审 |
| ⑥ 工程件 | 磁盘缓存 + 超限二分 | opt-in sqlite 持久缓存（实测复跑同文本 **0 请求**）；请求撞尺寸上限自动对半拆分重试；S6 流水线化评估后暂缓 |
| ⑦ 扁平模式 | `flatten_fragments=True` | 可选输出模式：丢同型碎片、合并被分隔符拆开的同型相邻实体，服务平面金标场景（默认关闭，嵌套输出不变） |

## 2. 识别准确率对比

### 2.1 冻结 test 集（600 句，同模型同参数）

| 数据集 | 0.1.0 F1 | 当前 F1 | 提升 | 精度 P | 召回 R | 预测数/金标数（0.1.0 → 当前） |
| --- | --- | --- | --- | --- | --- | --- |
| MSRA | 0.605 | **0.720** | +11.5 | 0.471 → 0.717 | 0.844 → 0.722 | 484/270 → 272/270 |
| Resume | 0.210 | **0.326** | +11.6 | 0.136 → 0.296 | 0.460 → 0.364 | 2305/681 → 839/681 |
| CLUENER | 0.341 | **0.520** | +17.9 | 0.246 → 0.488 | 0.552 → 0.556 | 994/444 → 506/444 |
| 24 语言扫描 | 24/24 | **24/24** | — | — | — | — |

要点：

- **提升主要来自精度**：0.1.0 对每个候选子 span 独立打型，碎片只要自己拿到 0.5+ 概率就混入输出（预测数最高达金标的 3.4 倍）；当前版本里这些碎片在竞争提名中被完整实体压制、被 PARTIAL/MIXED 否决、被本地剪枝拦截，预测数收敛到与金标几乎 1:1。
- **召回小幅让渡、净收益为正**：MSRA 召回 0.844→0.722（嵌套/碎片被清理的代价），但 F1 净升 11.5 点；CLUENER 召回持平。
- 归因（dev 集分阶段）：schema 工程单项贡献最大（+12~+22），剪枝与竞争打型再叠加精度；每阶段均经 dev 集 A/B 门禁。

### 2.2 长文档质量（15k 字实测）

0.1.0 在多窗口（>12k token）下存在**偏移缺陷**：token 偏移是源文本全局的，但打型以窗口文本切片，第二窗口起 span 全部错位——**旧版长文档输出本来就是错的**，无质量可比性。当前版本逐实体断言 `text == source[start:end]` 全过，关键实体全部命中。旧版该负载输出 3150 个实体（含错位垃圾与全部存活碎片），当前 2042 个（经提名与否决精审）。

## 3. 速度对比（实测）

### 3.1 头对头（worktree 检出旧版，同机同参数同负载）

| 负载 | 0.1.0 | 当前 | 差异 |
| --- | --- | --- | --- |
| 20 句短文本**串行**调用 | 99.0s | 166.0s | **+68%（更慢）** |
| 15k 字长文档**单次**调用 | 842.7s（≈14 分钟） | 506.7s（≈8.4 分钟） | **-40%（快 336s）** |

为什么方向相反——两类耗时结构不同：

- **长文档**：旧版检测批在窗口内**串行**（约 145 批 × 2 窗口的往返逐个排队），是绝对瓶颈；当前版本检测/重查/打型全部并发 + 邻域缓存 + 重叠窗口单飞去重（实测该负载缓存命中 5,849 次），结构性优势压倒一切。
- **短文本单句**：当前默认档（compete）的提名有 2–3 个**串行轮次**，单次调用的链路变长（旧版每句约 2–3 个往返，新版约 5–7 个）。**吞吐场景不受此影响**（多句并发时轮次互相重叠）：全量基准 600 句墙钟 712.5s → 596.0s（**-16%**），且是在 F1 大涨的同时取得的。
- **延迟敏感场景**：`JevNER(typing_strategy="flat")` 切回低延迟档——dev 集实测 flat 档墙钟比 0.1.0 算法还**快约 8%**（245.6s vs 266.0s），同时 F1 仍远高于 0.1.0（见下表）。

### 3.2 各配置的延迟-精度-成本全景（dev 集 150 句 + 24 语言）

| 配置 | 墙钟 | F1（msra/resume/cluener） | 输入 token |
| --- | --- | --- | --- |
| 0.1.0 算法（等价复跑） | 266.0s | 0.511 / 0.236 / 0.346 | 1.47M |
| 当前 + flat 档 | 245.6s | 0.683 / 0.346 / 0.575 | 2.06M |
| 当前 + compete 档（默认） | 371.1s | 0.675 / 0.344 / 0.580* | 1.96M |

\* compete 与 flat 在 dev 集上 F1 接近；test 全量上默认档综合最优（问题数 -48%、token -34% 的成本优势主要在长文与大体量场景显现）。准确率结论以 2.1 的 test 全量为准。

## 4. 成本对比

| 指标（全量基准 600 句） | 0.1.0 | 当前 | 变化 |
| --- | --- | --- | --- |
| 问题数 | 44,820 | 37,052 | **-17%** |
| 请求数 | 2,175 | 1,693 | **-22%** |
| 输入 token | 5.39M | 7.22M | **+34%** |

- token 上升来自 PARTIAL/MIXED/NONE 否决描述随题下发（阶段③的质量代价，短文本无法被邻域化对冲）；
- 长文档侧相反：邻域化 state + 对齐缓存 + 单飞把重叠窗口的重复问题消掉（15k 字负载实测缓存命中 5,849 次）；
- 磁盘缓存开启后，复跑同文本**零请求**（跨进程实测）；
- 0.1.0 没有任何用量计量能力（这本身是重要差异）。

## 5. 顺带修复的 0.1.0 缺陷

1. 自定义实体类型打型即崩溃（答案标签查注册表而非本次类型集）——`entity_types=[自定义]` 路线在 0.1.0 上不可用；
2. 多窗口偏移错误（见 2.2，长文档输出错误）；
3. `GENDER_BATCH_SIZE=256` 定义后从未生效（实际按 64 分批，性别批请求数 4 倍于设计）；
4. 窗口任务与打型批共用线程池的理论死锁（协程化消除）。

## 6. 行为与 API 变化（相对 0.1.0）

- 公开导出的八个名字不变，`__call__` 签名向后兼容；
- 新增：`arecognize`/`aclose`/异步上下文管理器、`ner.usage` 计量、构造参数 `typing_strategy`（默认 compete）与 `disk_cache_path`、调用参数 `flatten_fragments`；
- `max_workers` 语义从线程数变为在途请求上限（默认值不变）；
- 嵌套森林输出语义不变（`flatten_fragments` 默认关闭）。

## 7. 已知权衡与后续方向

- 短文本单次调用延迟（默认档 +68%）：提名轮次流水线化（暂缓的 S6）是后续方向；
- 输入 token +34%（短文本）：否决描述的压缩措辞可再打磨；
- Resume 类密集细粒度场景仍有差距：正反例内容继续扩充、提名轮次自适应；
- 病态重复长文在 compete 档成本偏高：可用 flat 档或磁盘缓存缓解。
